ZIP Intake

          
适合新增单刊 zip，或一个 zip 内含多刊 release 目录的批量包。上传后只走 intake 链路与门禁校验，不会直接改 release artifact。

          

            
上传前先看

            
    
              
  • `auto` 适合绝大多数情况，只有在自动识别明显错路时才手动指定 Route Hint。
    • 
              
  • 如果 zip 文件名里混有月份、批次号、`release` 等噪音，建议显式填写 `publication_id`、`display_name`、`issue_label`，避免系统误推导。
    • 
              
  • 上传结果会先给出可转发的诊断摘要，再附原始 JSON，方便直接贴给内容处理同学。
    • 
            

          

          

            
            
            
`single_issue_batch` 适合 Reader's Digest 这类单刊批量 markdown；`multi_release_pack` 适合一个 zip 里含多刊 release 目录；`generic_split_release` 适合单刊且目录里有 `adult/youth/merged`。

            
            
            
            
            
            
            
建议默认勾选。适合需要保留原包审计、复盘、二次比对的绝大多数情况；只有你明确要保留在 inbox 里继续人工重试时再取消。

            
            
默认不允许静默覆盖旧期次。只有在修订同一刊同一期旧上传时才勾选；系统会先备份现有 issue，再做替换，若导入失败会自动回滚。

            
            
只有在内容包已经通过门禁，且你确认这期应该进入当前候选版本时才勾。若只是试传、校验结构、或等内容补稿，别勾。

            
            
这是最高风险选项。只有在内容已通过门禁、已纳入 candidate、并且你准备立即把当前线上 current 切到最新候选时才勾。日常试传、补录、门禁排错不要勾。

            
          

          

        

        

          
Import Notes

          
推荐操作是直接上传 zip。后台会先落到 `ops/intake/inbox/`，再调用 intake action layer，保留 manifest、scenario 与审计轨迹。

          
如果返回 `CONTENT_PACKAGE_GATE_BLOCKED`，说明系统已经读懂包结构，但内容本身不满足导入门禁；这时要根据摘要里的 blocker codes 去补内容，而不是继续改 route。

          
如果是修正旧上传，不要先手删旧 issue。请勾选“替代现有期次”，并填写明确的 `publication_id + issue_label`；系统会先备份再替换，失败自动回滚。

          
如果返回 `ENOENT` 或结构类错误，优先检查 Route Hint 与 zip 目录结构是否匹配，再检查是否遗漏 `adult/youth/merged` 目录。

          
“纳入当前 release candidate” 会尝试把新 issue 加入候选版本；“直接发布五刊 current” 会进一步触发候选发布。只要导入本身失败，这两步都不会执行。

Safety Notes

          
所有 stateful CRUD 动作都走 file-backed action layer，继承 TEST2 锁与原子写规则。

          
OPS5 不编辑 immutable release artifact，不把 mobile 用户页面变成后台。

          
article metadata 仅写 override，taxonomy 仅写映射，scenario membership 仅写候选构成。
